# 服务端训练管理升级方案

日期：2026-10-16。状态：设计基线；R1–R3首版核心已实现，R4/R5待实施。

更新（2026-10-17）：用户已要求连续推进，并单独批准隔离测试库新增表与独立账号缓存。R2/R3 首版核心已有实现及隔离验收；实际范围与结果见 [首版交接](training-v1-handoff.md)。下文保留设计基线，未完成的R4/R5不视为已交付；当前运行库未迁移。

本文接续已完成的本机 P0–P4 工程版，设计下一阶段 R1–R5。目标是传统的前后端分离业务系统：后端管理账号下的正式训练数据，前端负责交互、本地缓存和离线待提交内容。既有备份、快照和 Agent 不推倒重做。

最初方案撰写轮次仅修改文档；后续经用户要求已实施隔离首版。没有迁移真实数据或当前运行库，不调用付费模型、不公开发布。方案确认不替代 AGENTS.md 要求的数据库、凭据及发布具体授权。

## 1. 目标与交付边界

用户在手机添加动作、记录一组、结束训练后，无需手动导出上传即可保存到账号；换设备登录后可以查看已同步历史。断网时仍能记录，恢复后补传，并明确显示同步状态。

后端需要拥有完整的训练创建、修改、完成、查询、权限校验与并发控制能力，而不是只接收备份文件。服务器确认成功的版本是云端权威版本；尚未确认的本地内容是待提交修改，不能显示为已上云。

### 1.1 首版 R1–R3

- 单设备编辑训练，多设备读取历史；其他设备不能直接接管正在进行的训练。
- 力量训练的开始、加动作、加组、修改、完成，以及既有有氧/休息日表达的兼容。
- 本地持久化待提交内容；断网、刷新、会话过期和响应丢失后可恢复。
- 所有用户自定义动作至少具备首次创建/认领映射能力，不能让训练依赖只在手机存在的动作。
- 已同步历史可在其他设备分页查看；旧数据导入需预览与用户确认。
- 模板、体重、照片的完整云端管理及实时统计/Agent 接入属于后续范围；界面必须说明哪些字段尚未上云，不能暗示整机数据已同步。

### 1.2 完整版本 R4–R5

- 动作库、模板、每日体重的服务端 CRUD 与缓存；已完成训练的受控编辑、软删除和跨设备变更拉取。
- 照片独立上传下载与配额；训练详情恢复时字段完整。
- 实时业务统计、明确版本绑定的 Agent 输入、云端模板应用。
- 手机实机、PWA 更新与离线验收，生产配置及恢复演练。

不做实时协同编辑、自动合并冲突、CRDT、微服务、分布式高可用或模型自动改写训练。首版不承诺两台手机同时编辑同一次训练。

## 3. 数据归属与运行方式

### 3.1 两种明确分离的空间

1. 本地访客空间：沿用旧库，无需登录可训练，不会登录即自动上传。
2. 账号空间：登录并明确启用后，使用以服务端用户稳定标识隔离的本地缓存与待提交队列。

切换空间时先检查正在编辑的训练和未同步数量，不能在原编辑页面中偷偷更换归属。退出后停止该账号同步、隐藏其数据；未同步数据留在原账号分区，重新登录同一账号才能继续。不向另一账号补传，也不自动清空旧访客库。

首次启用展示“保持本地使用 / 将本地数据导入当前账号 / 使用账号已有数据”。导入不是自动认领。共享设备上的账号缓存不等于加密存储，UI 需说明；本轮不承诺本地加密。

### 3.2 正常保存链路

```text
页面操作 → 统一仓储 → 本地事务保存缓存与 outbox → 显示本地已保存
                              ↓
                   同步器调用服务端写接口
                              ↓
                  服务端事务保存业务数据与版本
                              ↓
                本地事务确认并显示已同步
```

缓存更新与 outbox 登记必须同事务成功。同步调度可以合并尚未发送的连续修改，不能丢失用户最后一次输入。输入防抖只减少网络请求；切换页面、完成训练之前需刷新本地待保存内容，不能只依赖页面卸载事件。

同步状态：`LOCAL_ONLY`、`PENDING`、`SYNCING`、`SYNCED`、`AUTH_REQUIRED`、`CONFLICT`、`FAILED`。最后同步时间来自已确认的响应；不能靠本机时间判定云端更新顺序。

## 4. 服务端领域模型（审阅设计，非可执行 SQL）

新表使用 `live_` 前缀与既有快照投影区分，实际迁移编号以实施时最新版本为准；不修改 V1–V4。

| 数据 | 主要字段与约束 |
|---|---|
| `live_exercise` | 用户、ID、名称、部位、默认休息、版本、删除标记；预置动作标识稳定，用户修改互相隔离 |
| `live_template` / `live_template_item` | 用户、ID、名称、动作顺序与默认组次、版本；历史不随模板修改 |
| `live_session` | 用户、客户端生成 UUID、类型、业务日期、开始/结束时间、时区偏移、时长、状态、版本、编辑设备、备注、删除时间 |
| `live_session_exercise` | 独立 UUID、训练归属、动作 ID、名称与休息时间快照、顺序 |
| `live_set` | 独立 UUID、训练动作归属、顺序、重量、次数、完成标记、RPE、热身标记 |
| `live_body_weight` | 用户 + 本地日期唯一、体重、版本；兼容旧 session.weight，不重复计数 |
| `live_photo` | 用户、训练、对象标识、类型、大小、状态；不将 base64 放在常规训练请求中 |
| `training_mutation` | 用户 + mutationId 唯一、请求摘要、资源、结果版本/结果、到期规则；同键不同内容拒绝 |
| `training_import` / 导入映射 | 用户、来源标识、文件摘要、旧 ID→新 UUID、状态与摘要；可重入且不重复导入 |
| `training_change` | 用户内有序提交编号、资源/版本、删除标记；供增量读取，不包含完整敏感内容 |

所有资源访问使用认证上下文 user_id；关系引用必须验证同一用户与同一父训练，不允许仅凭子记录 ID 更新。重量等用定点数，范围、精度、空值、RPE、数组数量及请求大小在 R1 契约中逐项冻结。

保留动作名称/休息快照，有氧时长/距离、饮食、备注及旧日期语义；类型不能仅由 exercises 是否为空猜测。休息日导入按既有规则识别，歧义需报告。计时用时间点恢复，客户端时长为受校验的业务输入，不声称服务器能证明实际训练时长。

## 5. 写入、幂等与并发

首版以“一次训练”为聚合：前端每次同步提交有界完整训练内容，服务端在单事务内保存训练/动作/组、增加版本、记录幂等结果和变更事件。关系表并不要求每个按钮对应一个 HTTP 请求。

- 创建使用客户端 UUID 与 mutationId；新训练期望版本为 0。
- 更新必须带 expectedVersion；服务端比较并原子递增，不接受无条件覆盖。
- 同一用户同 mutationId 同摘要重试返回原结果；不同摘要返回冲突。先核验幂等命中，再判断旧版本，以处理成功后响应丢失。
- 同一训练串行发送；发送中的请求内容与 ID 冻结。新编辑生成下一份待提交内容，前一请求确认后才获得新的基准版本。
- 网络错误、超时及有限 5xx 做有界退避；401 暂停等待登录，409 保留草稿进入冲突，校验失败显示具体字段，不无限重试。
- 服务端提交与响应之间崩溃通过幂等恢复；不能宣称网络“恰好一次”。幂等凭证保留期和客户端自动重试期在 R1 固定，超期必须先查询资源状态再决定补交。
- 首版 active session 绑定编辑设备随机 ID；它只控制编辑流程，不能代替身份认证。不实现仅靠超时自动抢占；接管需联网确认并使用当前版本，旧设备提交返回冲突。
- 多标签同步可重复调度，但不能覆盖同一训练的未提交草稿；使用本地持久协调与版本检查，仍由服务端兜底。
- 冲突先提供“保留本地副本、查看云端版本”，不得默认最后写入获胜；不会自动创建两条已完成训练掩盖冲突。

完整聚合设置数量和字节上限，照片独立处理；如实测不适合再拆命令接口，不为展示 CRUD 把每次按键变成请求。

## 6. API 草案

沿用同源会话与 CSRF，前缀 `/api/v1`；以下为拟议路由，不与已实现接口混淆。

| 接口 | 职责 |
|---|---|
| `POST /workout-sessions` | 幂等创建，返回 ID、版本和规范化数据 |
| `PUT /workout-sessions/{id}` | 聚合修改/完成，mutationId + expectedVersion |
| `GET /workout-sessions/{id}` | 账号内详情，包含版本 |
| `GET /workout-sessions?cursor=...` | 分页历史，稳定排序与过滤 |
| `POST /workout-sessions/{id}/takeover` | 后续显式接管，版本校验，保留原设备草稿 |
| `DELETE /workout-sessions/{id}` | R4 软删除，版本/幂等校验，不硬删 |
| `GET /training-changes?cursor=...` | R4 按提交顺序拉取变更及墓碑 |
| `/exercises`、`/workout-templates`、`/body-weights` | 分阶段业务 CRUD，用户作用域 |
| `POST /training-imports/preview` | 上传/选择来源，校验、去重映射预览 |
| `POST /training-imports/{id}/commit` | 明确认领后执行，幂等；查询进度单独 GET |
| `/training-photos` | R4 独立附件流程，鉴权与配额 |

错误使用稳定代码：未登录 401、CSRF/操作拒绝 403、无权资源统一 404、版本/幂等/编辑冲突 409、过大 413、业务输入校验 422；与既有错误契约协调后冻结。所有列表有上限，写接口有账号级额度。分页游标不能由客户端自由指定用户。

增量序号不能简单使用可能乱序提交的全局自增 ID 当“已全部读到”的水位；R4 采用用户内事务串行编号与业务提交同事务，或经验证的等价实现。分页读取固定水位；游标过期必须完整重拉并保留本地 pending 草稿，不能直接覆盖。

## 7. 本地数据及旧用户迁移

1. 升级前保留旧站点 JSON 导出副本；原备份格式及原文件字节保持兼容。
2. 新 Dexie 版本只增加账号分区缓存、outbox 和映射；原四表保留，不在 upgrade 内调用网络或批量认领数据。具体 stores、事务范围和容量预算先单独审阅。
3. 预览本地数据/选定云备份：动作、模板、训练、体重、照片数量，无法支持字段及重复/冲突项；用户选择导入目标账号。
4. 来源摘要与导入映射稳定保存；旧 ID 不保证 UUID，组/动作以首次持久映射生成 UUID，重试不得重新随机生成。
5. 同一来源同内容不重复创建；相同旧 ID 不同内容进入冲突，不静默覆盖。不同来源缺乏可靠身份时只提示相似，不按名称日期自动合并。
6. 批次可恢复；每个训练原子提交，整个导入可能分批成功，报告成功/失败/待处理数量。部分失败不能宣称全成功。
7. 核对数量、字段、统计、抽样详情和附件；经确认再默认进入账号空间。旧访客数据仍保留。

首版未支持的模板/体重/照片保留本地与原备份，并在预览中明确“未迁移”；不得显示为全量迁移完成。若用户要求换手机完整恢复，必须等 R4 字段闭环再交付这一承诺。

## 8. 统计、Agent 与备份的演进

- R1–R3 保留原快照分析与 Agent，UI 标明“快照数据”，不冒充实时统计。
- R4 新建基于 live 表的查询，复用有效组、容量、日期语义及共享夹具；修改/删除后的统计有相应测试。
- Agent 任务创建时绑定一个不可变数据版本或物化上下文，避免执行中训练更新导致工具前后矛盾；只发送必要结构字段，不发送照片、备注或完整备份。
- 已有草案继续绑定旧快照；新来源显式区分，不改写历史建议依据。云端确认/应用模板使用独立幂等事务，不允许模型直接写训练。
- 用户导出的兼容备份、原始不可变云备份和数据库灾备继续保留；业务数据库不是备份的替代品。

## 9. 实施结构与阶段验收

以下目录为拟议职责，获批实施前再登记实际目录规范，不创建占位模块。

- 后端 `workouts/` 管理训练聚合；`catalog/` 管理动作模板；`bodyweight/` 管理每日体重；`trainingimport/` 管理导入。既有 `training/` 暂保留只读快照职责。
- 前端 `src/data/` 统一仓储，`src/sync/` 管理账号分区/outbox/拉取，HTTP 仍集中 `src/api/`。
- 契约放 `docs/contracts/`，迁移审阅 SQL 先放该目录，不直接放 Flyway；测试按现有业务包及 contracts 约定组织。

| 阶段 | 内容 | 完成标准 |
|---|---|---|
| R1，约 1 日 | 写入口清单、字段/状态/API/SQL/Dexie 审阅、风险与测试设计 | 契约可审阅，明确授权范围，无真实数据修改 |
| R2，约 1–2 日 | 后端聚合写入、权限、幂等、版本、分页与动作映射 | 真实 PG/HTTP 验证，包括并发与响应丢失重试 |
| R3，约 3–4 日 | 仓储、本地队列、账号隔离、训练页与历史联调、迁移预览、手机回归 | 离线刷新不丢记录、补传无重复、另一设备可查看；部分迁移明确展示 |
| R4，约 3–5 日 | 动作模板体重、附件、编辑删除/变更拉取、业务统计与 Agent | 完整字段跨设备闭环、旧快照兼容、无静默覆盖 |
| R5，约 2–3 日 | 生产适配、恢复、PWA/手机实机、交接 | HTTPS/会话、备份恢复、更新期间 pending 数据验证；正式发布另行确认 |

R1–R3 估算 5–7 个工作日；完整范围约 10–15 个工作日。按单人串行工作、既有基础可复用估算，R1 后复核；服务器资源等待、域名配置等待和新发现的兼容缺陷不作为已保证工期。公网手机可用还依赖实际部署，不以本机验收替代。

## 10. 必须通过的验证

- 后端 Wrapper verify、真实 PostgreSQL；两账号越权读写、跨父记录引用、同键并发、版本并发、事务失败无半条训练。
- 前端 build/lint、既有统计/会话/模板回归；新仓储及队列验证失败、重试、乱序响应、两标签、401、退出/切换账号。
- 本地 schema 与导入变更按 CLAUDE.md 完整回归；使用合成旧版本备份和冲突输入，不复制用户真实备份做测试。
- 实际断网/恢复、页面刷新、锁屏恢复、PWA 升级有待提交记录；未缓存首次访问无离线能力，不能夸大。
- 在用户实际手机浏览器/PWA 验证加动作、加组、备注、有氧、完成与历史；桌面窄屏不能替代实机。
- 迁移前后记录/组数、统计、名称快照、休息设置、日期、附件一致；重复执行不增加数据。
- 旧快照、下载、既有 Agent 不回归；新链路默认模拟模型，不扩大现有付费预算。
- 恢复演练覆盖新增表、映射和幂等结果；数据库恢复之后客户端如何识别游标失效与待提交版本必须有用例。

## 11. 切换、回退与授权检查点

先独立测试环境验证，再显式为账号启用。未启用者继续原逻辑；不能同时向旧库和新库无条件双写后期待自然一致。

数据库迁移只做兼容新增，旧服务仍能读取旧数据；不因此承诺旧前端能展示新云端训练。回退时停用新入口并保留新云数据与 outbox；先导出、核对和提供查看方式，不删除新表、不回滚用户记录、不清空缓存。

实施前需要确认：新方案范围；新增数据库表/执行目标；Dexie 增量迁移与认领交互。真实旧数据导入由用户明确选择并确认。公开发布、凭据和系统配置单独审阅；本次撰写授权不包含这些操作。

每阶段输出简要交付说明，写清实际通过的检查、尚未完成部分及下一步；不沿用旧版 102 项结果证明新功能通过。
