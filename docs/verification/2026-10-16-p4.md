## 应用冷恢复

[P4RecoveryIT](../../server/src/test/java/io/github/cgz4526/workout/P4RecoveryIT.java) 纳入 Wrapper verify：

1. 启动全新源 PostgreSQL 与测试 JAR，通过真实 HTTP 注册、登录、上传共享合成备份并等待投影完成。
2. 构造明确标注的草案持久化夹具，通过真实 HTTP 确认，再停止源 JVM。此草案用于恢复验证，不算真实模型生成。
3. 源 JVM 停止后写入一条过期 RUNNING Agent 夹具，以便验证由恢复后的调度器处理。
4. pg_dump custom 导出到忽略目录，恢复到不同容器、不同数据库地址的新 PostgreSQL。启动新的 Java 进程，而非重启原库。
5. 验证原 JDBC 会话继续可用、备份下载原字节一致、训练容量 770、已确认草案及确认重放一致；退出后匿名访问 401，重新登录和下载正常。
6. 过期 Agent 标记 FAILED/MODEL_OUTCOME_UNKNOWN，model_calls 保持夹具值 1，不生成新草案，不重放付费请求。

最终批次 f2b2a0ea-0c17-441a-9fff-874aa00052df，归档 37,929 bytes，SHA-256 为 25e5a301f80520cf0e729b74698c35e0cfacab875e9219cc01b919bfc7703ffb。观测总耗时约 14.87 秒，包含测试库、JVM 启动、导出恢复与业务核对，不是生产 RTO。

共享 [测试 JVM 支撑](../../server/src/test/java/io/github/cgz4526/workout/TestApplicationProcess.java) 明确移除继承的模型密钥及外部 datasource 覆盖。普通 Spring 集成上下文也显式禁用真实模型配置；原 P2 进程强杀测试继续通过。

## 后端兼容回退

[P4RollbackProbe](../../server/src/test/java/io/github/cgz4526/workout/P4RollbackProbe.java) 是显式探针，不要求默认 verify 具备历史镜像：

- 使用本机 workout-server:p2 镜像内的历史 JAR，只读复制到忽略目录；临时提取容器不启动，按本次唯一标签核对后回收。
- 在自己的合成 V4 库中执行当前 P3 JAR→历史 P2 JAR→当前 P3 JAR。
- 三段均检查应用就绪；P2 和恢复 P3 后检查同一会话、原始下载及容量 770；P3 草案记录未丢失，恢复 P3 后可以读取。
- 数据库保留 V4，不执行降级迁移或 clean/repair；旧 P2 在其现有 Flyway 策略下能启动。没有因此修改迁移校验策略。

范围仅为本次两个后端版本和合成数据。未验证前端镜像配套回退、其他历史版本或生产切换；运行 P2 时 P3 功能不可用。不能推断任意数据库变更都可通过切换镜像回退。

## 三档数据与采样方法

[P4LoadProbe](../../server/src/test/java/io/github/cgz4526/workout/P4LoadProbe.java) 显式执行，独立 PostgreSQL 与 Java 进程，模型关闭。环境：Windows、i7-13700KF/24 逻辑处理器、宿主物理内存约 15.8 GiB、Docker Desktop 29.4.3/约 7.67 GiB 可用内存、Java 17、测试服务最大堆 256 MiB、连接池上限 8、PostgreSQL 17.6。测试数据库未配置与部署环境相同的容器内存上限。

同一合成用户上传三份备份，三份投影共存。每次训练单独日期，每组均完成、非热身，重量 40、次数 10；每日体重为空。统计查询不指定日期，读取该份完整快照；每个响应同时校验容量，错误/错误数值不算成功。

### 查询计划

通过 MyBatis XMLLanguageDriver 直接展开现有 TrainingMapper.summary 的真实 SQL，参数绑定同一 backupId 与空日期，执行 EXPLAIN (ANALYZE, BUFFERS)。最终三档观测执行时间分别为 0.354 / 4.266 / 31.109 ms；它们不是完整 HTTP 时间。

大快照覆盖绝大多数现有训练记录，计划对 snapshot_session 使用顺序扫描、CTE 与聚合。此处没有为追求“使用索引”而添加索引，也没有据此声称已完成查询优化。
